# Phase one design

Go 1.25+ module `github.com/i2bskn/authlume`. Two independent standard-library packages. Only the application composes them. An opaque nonempty subject string is the sole application identifier. The application owns identifier normalization, enrollment rules, authorization, account lifecycle, throttling and its database schema.

## Password authentication

* `password.Hash` generates a fresh 16-byte salt with crypto/rand. Records use a versioned PBKDF2-HMAC-SHA256 encoding with 600,000 iterations and a 32-byte result. The v1 verifier accepts exactly these parameters and canonical fixed-size base64 fields before performing any derivation, and compares the result in constant time. This choice uses Go's standard crypto/pbkdf2 and the OWASP work factor for SHA-256. A different cost or algorithm needs a new record version. Passwords are opaque bytes in Go strings, bounded at 1–1024 bytes and never truncated.
* The application supplies a context-aware lookup (subject and encoded hash, distinguished missing-account error) and a mandatory post-password policy callback. Missing-account and wrong-password results both return ErrCredentials. A missing account performs equivalent dummy KDF work. Corrupt records, store errors and policy errors fail closed and remain distinguishable internally. Applications return generic errors and never log credentials.
* Policy chooses PasswordOnly or RequireMFA for the verified subject. An empty or unrecognized decision fails closed. Authentication returns subject and decision only after verification and successful policy evaluation. A RequireMFA result represents an incomplete login. Phase one issues no challenge tokens. Only an explicit PasswordOnly branch in the sample calls the session issuer. Password has no cookie or session API.

## Web sessions

* After a complete application-authorized authentication, Issue creates a fresh 32-byte random ID, sets an unpadded base64url cookie and stores only its SHA-256 digest as key. Server state includes subject, authentication time, last activity, fixed absolute expiry and idle lifetime. Empty subjects and invalid configurations fail closed. The cookie is host-only, named __Host-authlume, with Path=/, Secure, HttpOnly, SameSite=Lax and an expiry at the absolute deadline. Duplicate or noncanonical cookies return ErrInvalid on Read, Touch, Issue and Logout, without changing store state or writing headers. Absent cookies allow Issue and idempotent Logout. Backend errors propagate independently of invalid sessions. Write headers only after successful persistence.
* Store has three atomic operations. Replace checks new-key uniqueness and consumes any presented previous key while inserting the freshly authenticated state in the same transaction. A missing old record permits a new, independently completed login. Use atomically reads, checks both deadlines and optionally touches a live record. Delete idempotently revokes by digest. Operations on the same keys must be linearizable. A touch cannot recreate deleted/expired state. Time never moves last activity backwards. Compare now >= deadline for expiry. In-flight requests already authorized can finish. Implementations may remove expired records in Use and must arrange physical cleanup. MemoryStore serializes operations, has bounded capacity, and reclaims expired entries before reporting full. Persistent/shared stores implement the same contract.
* OSS defaults are idle 24h and absolute 7d. Apps configure positive durations with idle <= absolute. The i2 application profile sets idle 7d and absolute 30d at the call site. Read validates without touching. Only an explicit server-selected interactive action uses Touch; the app must distinguish actual user actions from polling, prefetch and keepalives. No request header or query flag chooses the activity classification.
* Logout deletes server state before clearing the cookie (same attributes, past expiry). Store failure must not appear to complete logout. A server-side Revoke accepts the stored digest independently of HTTP. Service-wide account revocation requires an application-maintained subject index or equivalent store functionality.
* Sensitive operations check authentication age against an app-defined maximum after validating the session. Activity never refreshes authentication time. A stale session requires a complete fresh authentication under current policy for the intended subject, followed by Issue to rotate the ID. A new completed login starts new idle and absolute windows. Applications bind any multi-step authentication to the initiating user and action. No standalone reauthentication protocol is included.

## Example and verification

A runnable loopback-only TLS sample uses net/http with method-specific routes, origin protection for unsafe requests, and one app-owned demonstration account. No hardcoded password. It shows login, a protected page, a passive polling endpoint, explicit user activity and POST logout. Interactive HTTP tests drive the actual handler using TLS, a cookie jar and a controlled clock. Cover expiry at equality, background reads, renewal capped by absolute expiry, rotation/revocation, policy denying session issuance and store failure. Unit tests cover package boundaries, parameters, errors and concurrent store behavior. No provider integrations, application migrations or legacy formats.
